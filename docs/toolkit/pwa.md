Makes the public build installable and playable fully offline. `vite build` runs the `pwa` plugin, which adds the manifest and icon tags to `index.html` and writes `manifest.webmanifest` (standalone, scoped to the build's base), `sw.js` (the service worker, with this build's id) and `pwa-assets.json` (every file of the build with its size and content hash, plus the build's version and id). The dev server serves no worker.

**A normal browser visit loads exactly as before.** The worker registers but steps aside (no request is intercepted, no list is fetched) until a whole build has been downloaded into an offline set. The download starts only when the game runs as an installed app (`display-mode: standalone`, or `navigator.standalone` on iOS) or when the player taps "Download" in Settings (Offline).

**The offline set**: `src/dev/pwa.js` fetches every file in `pwa-assets.json` (music and voice included; one sound format per browser, Ogg Opus where the browser plays it, else m4a, about 48 MB on Chrome) four at a time into a cache named for the build (`hitl-set-<id>`), retries a failed file three times, skips files an earlier try already stored, and writes a completion marker last. A cut-off download pauses ("Download paused") and resumes on the next launch or when the connection returns; a set without its marker is never served. A small pill shows "Downloading for offline: 34% of 48 MB", then "Ready to play offline" (it hides while any modal such as Settings is open; Settings shows the same state in its Offline row). `window.__HITL_OFFLINE` has the state (`state.state`: off, checking, downloading, paused, ready, error), `start()`, `peek()` (the size, for Settings) and `subscribe(fn)`.

**Serving**: the worker keeps one set active and serves everything it holds from it, pages included (the query is ignored, so `?seed=` works), answers range requests (audio seeking) from the cached whole file, and sends anything the set lacks to the network. The first complete set becomes active by itself; a later one only when the page asks (the player chose Restart), so a release never takes over silently.

**Updates**: on every launch of an installed app (or of a browser that holds a set) the page fetches `pwa-assets.json`; offline, that fails silently and the game starts from the cached version. When the list's version differs from the running build's, the new set is built in the background (its requests carry `X-Hitl-Download`, which makes the worker let them through to the network): a file whose content hash matches the same file in a complete set already stored is copied from there, and only the changed files cross the network (a release typically changes the hashed bundles, a few MB of 48; music and models are copied). With the browser's data saver on, an update is held back and Settings offers "Update (N MB)". When the new set is whole it asks "A new version is ready. Restart to update?" with Restart now or Later; both builds' sets coexist until then and the running one keeps serving, so a cut-off update never leaves a half-updated build. Restart makes the new set active and reloads. Once a build is running, every set that is not its own or the newest published one is deleted, partial downloads of superseded builds included. Saves live in `localStorage` and load on the new build through the sim's own migration.

**A launch that does not boot never sits blank.** After the page boots it tells the worker (`healthy`). A page the worker answered from a downloaded set (or from the network while recovering) carries a `Server-Timing: hitl-set` entry, which arms an inline watchdog in `index.html` (`scripts/pwa/boot-watchdog.js`). Once the page has been visible for eight seconds without reporting ready (or it reported a boot error) the watchdog tells the worker it stalled and reloads; time spent hidden never counts, and a page the worker did not serve from a set is never touched. The worker counts the stalls since the last `healthy`: after one, the next load fetches the page from the network first (five seconds), so a fixed release replaces a broken one; after two, the previous complete set becomes the active one (a build that throws while its modules load never reaches the page code that looks for updates). After two automatic reloads the page shows "Loading failed." with a Retry button over the blank screen, and takes the card away if the game comes up late. A page's cache read that does not answer in four seconds (twenty for a file) is treated as a miss and goes to the network.

`npm run pwa-check [--real [<from> <to>]]` builds versions of the game and drives a phone-sized Chrome (GPU slot) through: a plain visit makes no request beyond the worker and manifest and stores no set; Settings downloads on request with its size and progress; the installed app downloads with a progress pill, a cut-off download pauses and the next launch resumes, "Ready to play offline" shows, Chrome reports no installability errors; with the network off the game boots, a new game in the dotcom era plays its music files from the cache and runs weeks; a new release downloads while the old one runs (only the changed files, counted at the server), a cut-off update leaves the old version working, the prompt appears when complete, Restart now runs the new version, an old-version save loads, the old set and any partial one are deleted; an offline launch after the update shows no prompt, pill or error; the data saver holds an update back until Settings asks; a release whose entry throws is replaced by a fixed one on the next online launch, which then also starts offline. `--real` additionally updates between two real consecutive commits (default: the two newest first-parent commits of `origin/main`, each given this tree's offline files and built) and prints the files and bytes transferred. Screenshots go to `--out` (default `shots/pwa`). `scripts/pwa-plugin.test.sh` builds with two bases and checks the generated files, their hashes and the sound-format filter (it runs in local CI).

`npm run pwa-webkit` runs the install, update and recovery paths in WebKit, the engine of every iPhone and iPad browser (about two minutes, no GPU slot; the game's WebGL is stubbed, the page, worker, caches and boot report are real). Closing the page stands in for closing the app: the first launch downloads a set and the next is served by the worker with no "Loading failed" card; a launch closed midway through an update download leaves the old set, and the next launch finishes the update and asks to restart; Restart runs the new build; with the server gone a launch boots from the cache; a page hidden past the watchdog's wait is left alone, and one controlled by the worker with no downloaded set is never reloaded; a worker whose cache listing never answers is stepped around; a build whose modules throw is replaced by the fixed one over the network by the page's own reload, lands on the previous complete build when the network offers nothing better, and with nothing to fall back on shows "Loading failed." with Retry, which reaches the fixed build. The main guard's full run includes it. It exits 2 when WebKit does not start: `scripts/pwa-webkit-setup.sh` downloads the few Ubuntu libraries Playwright's WebKit needs into the browser's own folder (it changes nothing outside `~/.cache/ms-playwright`).

`scripts/pwa-icons.sh` rebuilds `public/pwa/` (192, 512, maskable 512 and the iOS touch icon) from `docs/readme/logo-square.png`.

A new top-level folder under `public/` is part of the set automatically (the list is every file of the build).
