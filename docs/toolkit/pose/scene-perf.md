## Scene sampling and performance verification

Scene checks raycast through per-mesh bounding-volume trees (`__fastRaycast`, in a harness page and on page-host alike, built without touching the game's geometry), which finds the same hits many times faster; `--slow-raycast` uses three.js's own raycast to compare, and waits on the page exactly as long. `--render-reference` uses the rendered stepping path for comparison, with identical frames, subjects, warmup, camera and seed. `--profile report.json` writes real-clock readiness, warmup and sampling times plus actual WebGL draw submissions in three phases: page initialization, bootstrap/warmup and sampling. The profile is separate from the unchanged pose JSON rows and threshold rules. Readiness includes harness startup but excludes lock acquisition; measure cold command latency externally through process exit and read lock wait from the render-lock log. Do not compare different workloads or warmed and cold dependency caches.

A real draw allocates lazy Three.js resources whose UUIDs draw from the seeded stream, same as loading a model does (see the harness's own reseed after model preload); a mode that draws changes every actor choice after it. Warmup reseeds the game stream right after it runs, so it no longer matters whether that warmup drew: the default mode never does, `--render-reference` always does (for a real, comparable rendered path), and both land on the same stream from there on. Sampling then asserts zero actual WebGL draw submissions across all page contexts, including offscreen portraits, from warmup through the end of the run; an unexpected draw fails the command. `--warm 0` leaves `--render-reference` with no warmup draw either, so its own first draw (and the resource allocation it triggers) lands after the reseed, inside the sampled frames; nothing passes `--warm 0` today, and a caller who does should not expect it to match a separate `--warm 0` run of the default mode. Cold browser, model and font startup remain a separate performance prerequisite this does not address.

By default the pass (`blender/checks/pose-scene-page.js`) runs on the studio engine through `scripts/studio/page-host.mjs`, in its own Node process on a 1280x800 Medium scene: no browser, render slot or draw, and `--profile` reports its warm-up and sampling times with no draw counts. To hold it to the browser, run the same request twice with `--json`, once with `--browser`, and compare the rows with `faceCovered`, `coveredBy` and label overlays set aside: every other field matches to floating-point rounding. `tests/tools/pose-scene-engine.full.test.js` keeps the measure controls on the engine: a staged printer jam through its beats with held-prop measures and emotes, a face blocker that must hide and then give back a face, and judge controls for an absent subject, a missing frame and an impossible rule.
