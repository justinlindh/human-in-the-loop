The seeded event index: bots play seeds 1 to 20 (balanced, sensible, allHumans) in the pure sim, and every decision (with the choice made), era change, office move, incident, launch, company party (`party`, a company-wide celebrate; its id is the event's `cause` when it carries one, else `party`) and so on is indexed by seed, bot, week, era and stage, with a save-state snapshot just before staged decisions, era changes and office moves. `find.js` prints where an event happens and its snapshot. It exits 0 with matches, 1 with none (`--json` prints `[]`), and 2 when it can't answer; with `--json` a refusal prints `{ "error", "kind" }`, where kind is `stale-index` (indexes exist, none for this sim code), `no-index`, `build-failed`, `bad-index` or `no-query`, so a caller never mistakes a stale index for "no such moment". Tools stage straight to it: `scene.mjs` and `dump.mjs` take `--moment '<query>'` or `--snapshot <path>`, and `sweep.mjs` takes `--moments 'q1; q2'`. The index lives in `~/.cache/hitl-ci/events/`, keyed by a hash of the sim, data and build code (including `play.js`); a tool asked for a moment builds it when those inputs change. Save/load adapter changes keep the index valid because its snapshots are raw state JSON. Use it instead of playing and scanning seeds by hand.

**Building and profiling.** `node scripts/events/build.js [--seeds 1-20] [--bots balanced,sensible,allHumans] [--weeks 1040] [--jobs N] [--force] [--profile report.json]`. A pool of workers discovers the events and snapshot checkpoints, then replays each deterministic game to serialize only the saved states. `--jobs` defaults to the available CPU count, capped at eight; lower it on a busy shared machine. Rows are sorted by bot, seed and week independently of worker completion order. `--profile` writes JSON with wall time and each seed/bot's simulation, event extraction, serialization, compression and filesystem time in milliseconds, plus final index sorting, serialization, compression and I/O. Per-run timings sum across workers and include both simulation passes; startup and scheduling are included in wall time.

The cache location can be overridden with `HITL_EVENTS_DIR`. Build options select the runs for a new index; an existing index for the code is reused unless `--force` is supplied. A build writes into a private staging directory and publishes only after every worker, snapshot, index and metadata write succeeds. Interrupting with SIGINT or SIGTERM removes staging files and leaves any existing index intact. SIGKILL can leave a hidden `.build-*` directory, which is never read as an index. On every valid build invocation, including a cache hit, directories with an owning PID in their name are removed when their modification time is more than five minutes old and that process is gone. Live owners, permission-denied PID checks, recent directories and names without an identifiable owner are left alone. A successful build keeps the three most recent completed indexes. Invalid options or a failed build exit 2; a completed or reused index exits 0.

**Forced rebuild readers.** Publishing with `--force` first renames the existing directory to a backup, then renames staging into place. Between those two filesystem operations the index path is absent: a concurrent reader can report `no-index` or start a rebuild, and a read already in progress can fail. Retry after publication. A portable directory rename cannot replace a nonempty destination, so this swap is not atomic. Ordinary build failures restore the backup if publication fails; SIGKILL during the swap can leave only the backup until another build succeeds.

**Tests.** `npm run test:fast` uses one shared, short seeded fixture for replay, cache reuse and failure checks. `npm test` also runs `tests/tools/events-build.full.test.js`: all-bot reference parity, a long game with era snapshots, and one-worker versus pooled-worker byte parity. Run just those heavier checks with `npm test -- tests/tools/events-build.full.test.js`.

**State queries.** `--where '<js>'` is a predicate over the event `e` (its type, id and own fields, plus seed, bot, week, era, stage, staff) and that week's state `s` (after the tick, read-only). Every week also raises a synthetic `week` event, so a pure state condition is `--where "e.type === 'week' && s.outage?.weeks === 0 && s.office.stage === 1"`. Index rows that satisfy a predicate which never reads `s` answer it. A predicate that reads `s`, or matches no index row, needs states the index does not hold, so find plays seeds and bots for it: `--scan-seeds 1-60` (the default) by `--scan-bots` (the index's bots, or `--bot`), `--scan-weeks` deep (1040), over worker threads at a lowered priority, handing out no more runs once `--limit` matches are in. `--no-scan` refuses to scan; a plain query scans only with `--scan`. Each match is a snapshot of the state just before the tick that raised it, in the game's save format (`snapshot` in the row, and `snapshotFile` with `--json`), loadable with `--snapshot <path>` or capture's `pre` items, so the game's own loop plays into the moment. `--setup '<js>'` runs statements on the state each week before the tick (`s` in scope) and `--turn-while '<js>'` limits the weeks the bot takes its turn; both change the game that is played, and the snapshot carries their effects. Results are cached under the sim hash by query, so a repeat is instant and a larger `--limit` resumes. A predicate that is not JS exits 2 (`bad-query`), and one that throws while playing exits 2 (`scan-failed`, with the seed, bot and week). Exit 0 with matches, 1 with none, as before. Use it instead of a throwaway script that plays seeds.

**Look-ahead, ranking and unreachable conditions.** `--then '<js over e, s, m>'` keeps each `--where` moment waiting up to `--within` weeks (52) for a later event or week where it returns truthy: `--where "e.type === 'week' && s.outage?.weeks === 0 && s.office.stage >= 1" --then "e.type === 'incidentResolved' && e.weeks >= 2 && e.weeks"` finds an outage that lasts at least two weeks, which is only known when it resolves. `m` carries the moment's fields, `m.e` its event and `m.s` a copy of its state. The snapshot is still from before the tick of the `--where` moment, and a non-boolean `--then` result is kept as `result`. `--rank '<js over m>'` orders matches by a number, highest first (`--rank m.result` for the longest outage), and plays every seed in range to do it. Each run yields its first `--per-run` matches (1, or 5 with `--rank`), so a ranking is the best of those per seed and bot. When a scan finds nothing it says why: which `&&` part of `--where` no played run ever made true ("so no run played here reaches it": a mock scene or a bot change is needed, not more seeds), or how many moments matched `--where` and none satisfied `--then`. `--json --explain` prints `{ matches, scan: { runs, clauses: [{ expr, runsTrue }], unreachable, whereMatchesWithoutThen } }` as one value; without `--explain`, `--json` stays the bare list.

Scan notes: `--stage`, `--era`, `--weeks` and `--seed` apply to scanned events as they do to index rows, and `--choice`, `--prop`, `--snapshot` and `--pre` (index-only) are refused with exit 2 on a scan. `s` is not frozen, so a predicate that assigns to it changes the rest of that run. `--moment '<query>'` splits its query on whitespace, so a `--where` expression cannot go through it: stage a scan match with `--snapshot <path>` (`snapshotFile` with `--json`).

**Branching: act at the hit, play live, force a choice, veto.** `--branch '<js function body over s, e, m, sim>'` (with `--where`, instead of `--then`) plays each `--where` moment forward on a copy of its state (`s` is the state after the tick, `e` the event, `m` the moment's fields) and keeps the match when the body returns truthy; the returned value is the `result` for `--rank` and the output. `sim` has `dispatch(s, action)` (act at the hit: `sim.dispatch(s, { type: 'postMessage', id: 'meme' })`), `tick`, `botDecide`, `botTurn`, and `step(s, { choose })`, one live week: an open decision is answered from `choose` (`{ <event id>: choice, default: choice }`, so a misread outage's card can be answered with choice 2), then the tick, with no bot turn, as the capture page plays. `step` returns every event raised, so the body counts replies, and returning `false` the moment a decision card or an era change shows up is the veto. Example: `--where "e.type === 'week' && s.ops?.noc === 'agents' && s.outage?.misread" --branch "sim.step(s, { choose: { outage_unfixable: 2 } }); sim.dispatch(s, { type: 'postMessage', id: 'meme' }); let n = 0; for (let i = 0; i < 3; i++) { const ev = sim.step(s, { choose: { outage_unfixable: 2 } }); if (s.pendingDecision) return false; n += ev.filter((x) => x.type === 'chat').length; } return n >= 2 && n" --rank m.result`. The snapshot is still from before the tick of the `--where` moment; what the branch changes stays on its copy.

Every moment waiting on a `--then` is kept (up to 1000 at once per run); a scan that had to drop some and found nothing exits 2 (`scan-failed`) instead of reporting that none satisfied `--then`.

**Bot plan.** `--bot-js '<js over s>'` names the bot to play each week (default: the run's bot; `--bot` picks which runs), `--before '<js over s>'` runs on the state before the bot decides and again before its turn each week (for example `s.candidates = []` to stop hiring), and `--extra '<js over e, s>'` returns fields merged into each match's row (a desk count). Together they express a played-out setup such as "balanced until the consolidation era, then automateAll with no candidates": `--bot-js "['consolidation','plateau'].includes(s.era?.id) ? 'automateAll' : 'balanced'" --before "if (['consolidation','plateau'].includes(s.era?.id)) s.candidates = [];"`.
