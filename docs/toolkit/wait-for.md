Run after pushing to a PR, from the worktree that has the PR's branch checked out. It reads GitHub state only and never starts local CI; the auto-CI timer does that. It waits until every status the base branch requires (its branch protection, less `review`; local-ci stands in when the rules can't be read) and every GitHub check pass on the PR's current head, and exits 0, or exits 2 naming the failing check with the Local CI comment link. While the PR carries `ci-rerun`, an old local-ci failure on the head counts as still waiting, not failed. A cancelled GitHub check is not a failure by itself. GitHub can start two runs of a workflow for one head, and the workflow's concurrency cancels one: a cancelled job in a run that a newer run for the head replaced is waited past, and the log names both runs. When the newest run has cancelled jobs and nothing for the head is still running, it reruns that run's failed jobs once per head (`gh run rerun <id> --failed`; a marker under `~/.cache/hitl-ci/wait-for-reruns` holds the one rerun across restarted watchers), says so, and carries on. A job cancelled again after that rerun fails the wait, as does any real failure beside a cancellation. When the PR falls behind main or conflicts, it merges `origin/main` into the branch (a merge, never a rebase), runs the tests related to the branch's changes (`nice -n 10 npm run test:push` where `package.json` has that script, else `npm test`, or `--test`; the PR's required GitHub `test` check runs the whole suite on the pushed head), pushes, and waits on the new head. A conflicting merge is aborted (exit 4) and a failing test run is left unpushed (exit 5). It refuses to update from a worktree that isn't a clean checkout of the PR's branch at its head (exit 7). `--merged` keeps waiting until the PR merges; `--no-update` only reports a PR that is behind (exit 3); it is for local experiments only, and bash-guard refuses it (a PR whose watcher doesn't merge main never merges). It warns once when local-ci hasn't reported on the head within `--pickup` minutes (default 15; a CI slot can be busy). `--issue <n>` waits for an issue to close, or a pull request to merge or close, for work gated on another lane's fix. Wrap long waits in `timeout`, or pass `--timeout <min>` (default 240; exit 124). `--repo justinlindh/humanintheloopgame-site` waits on a site PR (run it from a checkout of the site repository if it may need updating); that repository requires `check` and `commits`, and has no local-ci.
PR state is polled from the shared snapshot (`scripts/tools/pr-snapshot.mjs`, refreshed about once a minute for all readers), so it can be a minute or two old; a PR that is no longer open, a `--repo` wait or an unreadable snapshot uses `gh pr view`, and `HITL_WAIT_SNAPSHOT=0` forces that. Every exit and every branch update is decided again on a live `gh pr view`, so a stale snapshot never ends the wait, and a live head the snapshot hasn't caught up with refreshes the snapshot. Right after a push GitHub can still show the previous head with its old results: while GitHub's head is an ancestor of this repository's `origin/<branch>` (refetched to rule out a force push), it waits for the pushed head instead of judging the old one.
It records the branch its worktree was on when the wait began and checks, before merging main and again before pushing, that the worktree is still on it; if someone switched the worktree meanwhile it exits 7 naming both branches and pushes nothing (a merge already made stays committed on the original branch).
