Standalone pose checks from geometry, with no rendering: plays one character through an animation, or a gesture over one (the facepalm over `typing`), and measures every frame in well under a second: each hand's distance to the face, the whole head and the top of the head (metres, hand centre to surface), and the face's angle to the game camera for any view. Prints a row every few frames and a summary over the gesture; `--expect 'hand0Face<=0.05@0.8'` holds a measure to a bound on a share of the gesture's frames and exits 1 when one fails. `--json` also carries a `joints` object on every frame: world positions for every named pivot the character rig has (`hips`, `torso`, `neck`, `head`, `legL`, `legR`, `armL`, `armR`, `wristL`, `wristR`, from `character.js`'s `joints()`), not just the four `probe()` fields (`eyes`, `forward`, `head`, `hands`) the printed table and `--expect` rules use. `--rig off` plays the procedural poses Low quality uses (the default plays the authored clips, as Medium and High do). `--root <worktree>` measures another checkout's render code with this tool, so a pose can be tuned in a lane's worktree before its PR. It runs the game's own character code in Node with two stand-ins (a canvas that draws nothing, fetch reading `public/`); `--check-browser` runs the same measures in a harness page and compares every number; the page serves the checkout the tool runs from, so it refuses `--root` (run the tool from that worktree instead). It needs `three-mesh-bvh`: after merging main, run `npm ci` if it can't be found. Tune a pose on these numbers, and render once at the end. `--scene` measures people in a staged scene instead (a mock with `--patch-js`/`--event`, an indexed `--moment`, or a `--snapshot`): per person and sampled frame, head-rectangle coverage by labels or emotes, facial landmark visibility, body visibility, face angle and projected head height. Its rules use `faceCovered`, `faceVisible`, `bodyVisible`, `faceCam` and `facePx`, for every person or one (`'s3:faceCovered<=0.1@0.8'`). It takes a render slot and draws nothing: warmup and sampling both run every real frame update through `R.render(dt, { draw: false })`, including camera, effects, matrices, CSS label projection and layout. `--render-reference` draws every frame instead, for comparison. Name the people you care about with `--who` to limit visibility rays.

`--scene --serve` keeps the browser and Vite server open across requests instead of paying their startup cost (most of a cold command's time) every time: pipe one JSON object per line to stdin, the same fields as the flags above in camelCase (`mock`, `moment`, `snapshot`, `patchJs`, `event`, `warm`, `frames`, `clip`, `every`, `who`, `view`, `rig`, `expect` as an array, `slowRaycast`, `renderReference`, `profile`, `json`), and it prints the same table, verdicts and `--json` rows a cold run of that request would, then a `POSE serve <n> code=<0|1|2> ...` summary line; send the next request only after that line arrives. Send `{"quit": true}` when done rather than relying on stdin EOF or closing the caller: it ends the session at once and frees the GPU render slot; a caller left open without it holds that slot until killed. Each request opens a fresh page rather than reusing one: a reused page's camera and character animation keep easing toward whatever the previous request left as their goal instead of starting fresh, so its rows do not match a cold run, and a fresh page's do. That still leaves per-request cost at page navigation plus model and font readiness, a few hundred ms rather than a cold command's 1.6 to 2.3 s. Getting closer to the sampling cost alone (roughly 300 ms) would need a render-side reset hook that puts a freshly-opened page's camera, character and clock state back to their start values on request, cutting page navigation and asset readiness out of the loop; nobody's asked for that yet.

Scene rules use all requested sample frames as their denominator. Every subject selected by `--who` or a rule prefix must have a sample at every requested frame; without `--who`, this applies to every discovered subject. Missing samples and an empty scene fail even without rules. A relaxed `@share` permits threshold misses, not missing samples. Both `--scene` and `--check-browser` reject a `--root` that differs from the tool's checkout. Run the tool from the checkout being measured.

For held props, scene rules accept `heldHeadDepth`, `heldTorsoDepth` and `heldGap`, in metres. Penetration uses the sweep's mesh tests with no tolerance; gap measures the wrist pivot to the prop surface. The measures cover all props carried by the selected person, taking the worst depth or gap. No prop gives null, so an absent grip cannot pass. Sample every frame with `--every 1`; start sampling when pickup has happened, and use `--expect 'heldHeadDepth<=0.000001' --expect 'heldTorsoDepth<=0.000001' --expect 'heldGap<=0.04'`. For the named hammer meshes, `heldPalmGap` measures the primary palm to the handle centreline, `heldSupportGap` the supporting palm to the shaft, `heldHeadDistance` the palm to the head centre, and `heldHeadJoint` the head to the end of the handle, all in metres. Use palm gaps <= 0.02, head distance 0.35 to 0.6, and joint gap <= 0.08. `heldHandleVisible` and `heldHeadVisible` ray-test the parts separately against the scene, including the holder, and reject offscreen samples. `heldShaftProjection` is the shaft length in the camera plane divided by its world length (>= 0.6 avoids an end-on handle). `heldHeadCross` is the head width perpendicular to the projected shaft divided by shaft length (>= 0.25 preserves the cross silhouette). `heldScreenDistance` measures the head-to-palm distance in the camera plane, in world metres, independent of zoom. Missing or hidden parts return null. These are geometric checks, not a substitute for inspecting the hold and its transitions. Rule output includes minimum and maximum values. Mock scenes accept `--rig off` for procedural animation.

Named targets use the bare head geometry in its local frame, transformed with the animated head. `hand0EyeLeft` and `hand0EyeRight` measure hand-centre distance to the head surface under each modelled eye centre (left is negative head-local x). `hand0Eye` selects the nearer eye. `hand0Brow` selects the nearer point at the upper edge of either eye; `hand0Forehead` is halfway from brow height to the head top. `hand0Mouth` uses the neutral mouth centre; `hand0Chin` is halfway from mouth height to the head bottom. All have `hand1` equivalents. These are point distances in metres, not distances to a broad region. Hats, hair and facial expressions do not move the targets. The original Face, Head and HeadTop surface measures remain available. Use `--expect 'hand0Eye<=0.04@0.8' --expect 'hand0Brow<=0.04@0.8'` for an upper-face gesture; a chin touch cannot pass those bounds. Geometric proximity does not prove a readable pose: inspect a final capture.

## Scene metrics

| Metric | Exact meaning and limitations |
|---|---|
| `faceVisible` | Fraction of seven equally weighted bare-head surface points reached from the current camera: left and right eye centres, left and right upper eye edges (brows), forehead, neutral mouth centre and chin. These are the named landmarks defined above, derived from the template's `head`, `eyes` and `mouth_flat` geometry. The live tagged head mesh's parent is the animated head pivot. Each sample transforms the points through that pivot's current world matrix. This is a sparse point fraction, not a percentage of face pixels or whole-head/body surface. A `>=0.9` rule requires all seven points. Small occluders between points can be missed. |
| `occluder` | Owner of the nearest opaque mesh before a facial point, counted across the seven rays; the largest count wins, with ties in landmark order. JSON `faceSamples` gives each named point's visibility, on-screen flag and blocker. Labels identify staff (including self), staged props, placed items, columns or walls. Merged furniture uses hit-position bounds to recover the placed item when possible, otherwise `furniture`; untagged geometry uses its mesh name or numeric id. This describes the face rays only. |
| `bodyVisible`, `bodyOccluder` | The game probe's separate whole-character vertex-sample fraction and dominant blocker. Meshes receive roughly six vertex samples each, not equal surface-area weights. The probe refreshes these every third call per actor, so they can lag consecutive frames. They never supply `faceVisible` or its blocker. |
| `faceCovered`, `coveredBy` | Largest fraction of the projected drawn-head rectangle overlapped by any one DOM bubble/label or emote rectangle, plus that overlay's label. The head includes baked hair and accessories; it is not the seven-point face region. Rectangles include empty corners, multiple overlaps are not unioned, and DOM positions come from the current frame's CSS projection and layout, including frames stepped without WebGL drawing. |
| `facePx` | Height of that same projected drawn-head rectangle in CSS canvas pixels, including hair/accessories. It is not facial feature size or physical framebuffer pixels. |
| `faceCam` | Game probe's angle in degrees between the animated head's forward vector and the camera direction. Zero faces the camera. This is orientation, independent of occlusion and text legibility. |

Facial visibility casts fresh rays every requested frame, from the camera near plane to each point, for orthographic or perspective cameras. Points outside the clip volume count as invisible with no occluder. Visible mesh ancestors and camera layers are respected. Own hands, hair, head backs and held objects can block the face. The attached baked eye/mouth decoration is excluded because it is the face marking over the sampled skin. Blinks, mood and mouth expressions do not move these neutral targets. A missing face template is an error, not a substitute body measurement.

Rays treat transparent materials with opacity below 0.5 as nonblocking; other visible mesh materials block. They do not evaluate texture alpha, shader opacity, shadows, smoke sprites, lines or points. DOM labels and emotes belong to `faceCovered`, not `faceVisible`. Use both rules and inspect a capture for final readability. Scene mode uses a browser harness and draws nothing; it does not promise subsecond command latency, which cold browser, model and font startup still bound.

## Projected scene JSON

Each scene JSON row retains its `frame`, subject `id`, metrics and rules, and adds `projected`. Use `--json scene.json` with the existing scene command. Projection uses the current game camera and current world transforms after each requested step. It does not change the player scene, introduce projection threshold rules or replace the existing metrics.

- `units: "css-pixels"`, `origin: "canvas-top-left"`: x increases rightward and y downward. `canvas` records CSS width/height and clientLeft/clientTop; add those offsets to get browser client coordinates. Values are floating point, independent of framebuffer resolution/device pixel ratio. The camera projection matrix includes its zoom, aspect and view offset.
- `face`: axis-aligned bounds of every triangle in the live drawn-head mesh, including baked hair and accessories. This is head geometry, not a skin-only face silhouette. `face.coverageRect` exposes the existing sampled-vertex head rectangle used by `faceCovered` and `facePx`, translated to the same canvas origin. Its sampling and lack of depth clipping are preserved for compatibility; it can differ from the exact triangle bounds.
- `hands.left` and `hands.right`: bounds of actual hand triangles within the baked arm mesh, excluding sleeve/arm triangles and held props. Anatomical identity follows the character rig: left is `armL` (hand0, negative character-local x at rest); right is `armR` (hand1, positive x). Identity never changes with camera direction or crossing hands. These are geometry bounds, not wrist points or palm-contact measurements. Both rig and procedural animation move the same baked meshes.
- Each geometric part has `status`, `rect`, `clippedRect` and `clipped`. Rectangles have `left/right/top/bottom`. Triangles are clipped to camera near/far planes before perspective division for `rect`; x/y can extend outside the canvas. `clippedRect` bounds those triangles after all six frustum planes, including intersections whose original vertices are all outside. `clipped` means some source geometry crosses or lies beyond a clip plane. `projected` means geometry intersects the clip volume, not that its pixels are visible. `offscreen` has null `clippedRect`; `rect` is also null when no geometry survives near/far clipping. Degenerate edge-on geometry may have zero width/height; missing geometry never gets a fabricated zero rectangle.
- `hidden` has both rectangles null: a mesh/sprite or ancestor is invisible, its camera layer is excluded, its material is invisible, or its transparent material has zero opacity. Hidden hands remain explicitly identified. A selected subject with no eligible visible head row remains absent, so the existing missing-frame failure still applies. Missing/duplicate arm tags, absent template geometry, unsupported baked topology, nonfinite coordinates or invalid canvas dimensions raise errors. Hand extraction validates arm-then-hand triangle counts and source shape against the chibi template before trusting the range; it does not guess a hand box from an arm's bounds.
- `overlays` includes all eligible scene DOM speech bubbles (`bubble`), stat labels (`stat`), other floating labels (`label`), and character emote sprites. It is repeated per subject so another person's overlay is available when checking a face. Each entry has a stable `id`, `subjectId`, `kind`, `text`, the rectangle/status fields and `overlapsFace`. That flag means positive rectangle overlap with this row's exact clipped face bounds. It does not imply depth occlusion or ownership. Emotes identify their subject and sprite; DOM labels have null `subjectId` because the renderer does not expose their follow target. Do not infer a speaker from proximity or text.
- DOM label IDs track pooled element identity for this measuring session, independent of text/order, and may be reused for a later utterance when the renderer recycles an element. They are not cross-run utterance IDs. DOM rectangles reuse `screen()` measurements of the inner element after the last render, including its CSS scale/translation; they omit pseudo-element tails, shadows and leader lines. The existing eligibility policy omits disconnected/display-none labels, opacity below 0.6, and dimensions below one CSS pixel. An empty overlay list means none met that policy. Labels are clipped to the canvas rectangle; emote quads use camera-facing sprite geometry including center, scale, material rotation and perspective size attenuation. Hidden emotes have null bounds, not a fabricated box. Text retains the existing 40-character diagnostic limit.

These bounds establish projected geometric extent and rectangular overlap only. They include empty corners and transparent texture regions, do not evaluate shader displacement, backface culling, depth occlusion, pixel coverage, font legibility or semantic readability, and cannot prove a hand covers an eye. Keep facial landmark visibility/contact rules and final capture inspection for those questions. The scene harness draws nothing and still takes the render lock; no subsecond latency is claimed.

## Scene sampling and performance verification

Scene checks raycast through per-mesh bounding-volume trees (the harness's `__fastRaycast`, built without touching the game's geometry), which finds the same hits many times faster; `--slow-raycast` uses three.js's own raycast to compare, and waits on the page exactly as long. `--render-reference` uses the rendered stepping path for comparison, with identical frames, subjects, warmup, camera and seed. `--profile report.json` writes real-clock readiness, warmup and sampling times plus actual WebGL draw submissions in three phases: page initialization, bootstrap/warmup and sampling. The profile is separate from the unchanged pose JSON rows and threshold rules. Readiness includes harness startup but excludes lock acquisition; measure cold command latency externally through process exit and read lock wait from the render-lock log. Do not compare different workloads or warmed and cold dependency caches.

A real draw allocates lazy Three.js resources whose UUIDs draw from the seeded stream, same as loading a model does (see the harness's own reseed after model preload); a mode that draws changes every actor choice after it. Warmup reseeds the game stream right after it runs, so it no longer matters whether that warmup drew: the default mode never does, `--render-reference` always does (for a real, comparable rendered path), and both land on the same stream from there on. Sampling then asserts zero actual WebGL draw submissions across all page contexts, including offscreen portraits, from warmup through the end of the run; an unexpected draw fails the command. `--warm 0` leaves `--render-reference` with no warmup draw either, so its own first draw (and the resource allocation it triggers) lands after the reseed, inside the sampled frames; nothing passes `--warm 0` today, and a caller who does should not expect it to match a separate `--warm 0` run of the default mode. Cold browser, model and font startup remain a separate performance prerequisite this does not address.

Run `timeout 300 nice -n 10 node blender/checks/pose-nodraw.mjs --json report.json` for exact rendered-versus-sampled comparisons across rig/procedural animation, two camera views, moving face blockers, held printer/hammer poses, moment beats, DOM bubbles and emotes through expiry. Add `--snapshot <file>` to verify the save/continueGame loading path too. The check preserves every row and field, compares camera/effect state, verifies that a rendered baseline fails the zero-sampling-draw assertion, retains missing-subject/frame and impossible-rule controls, and checks ordinary harness callers still draw by default. It takes the existing render lock automatically. Local CI runs it as the `pose-nodraw` step when a PR changes the renderer, the harness, the draw audit or a pose measure.
