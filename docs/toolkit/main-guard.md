Checks the newest commit of `main` with the full local suite (balance forced on) and one strict scene sweep. Sets the `main-guard` status on it; when main is red it opens or comments on one `main-red` issue, bisecting the merges skipped since the last green commit to name the first red one, and the next green commit closes it. New sweep violations seen only in seeded games go to a `sweep-finding` issue (art), and timing regressions against the previous main commit (checked at most hourly, filed after two bad runs in a row) to `perf-regression`; neither marks main red. It runs at the lowest priority, waits while others queue for the software render lock, records in `~/.cache/hitl-ci/main-guard/red` the steps red in two verdicts in a row on main's newest commit, so one flake holds nothing (auto CI holds render PRs while that names a render step), and keeps the shared checkout fast-forwarded when that is clean and idle, reinstalling its node_modules (`npm ci`) whenever `npm ls` finds them out of step with its lockfile. `pr-status.sh` shows its verdict first. It runs every 5 minutes as a systemd user timer from its own clone: run `scripts/systemd/install.sh` from the shared checkout to install it; `systemctl --user list-timers 'hitl-main-guard*'` and `journalctl --user -u hitl-main-guard` show it; `systemctl --user disable --now hitl-main-guard.timer` (or `install.sh --remove`) stops it. After local CI and the strict sweep it renders golden again with no check cache (`HITL_NO_CHECK_CACHE=1`, under the software lock), so a cache that wrongly skips a scene is caught on the next commit checked: a failure marks main red as `golden-uncached`, and its images (actual, diff, and the identity check's two renders) are kept for two weeks in `~/.cache/hitl-ci/main-guard/<sha>-golden/`, and one that fails on the machine gives no verdict. When local CI is red, its step logs are kept for two weeks in `~/.cache/hitl-ci/main-guard/<sha>-steps/`, and the `main-red` issue quotes each red step's FAIL lines (or its last lines when it prints none).
On a green verdict it also runs `scripts/events/prewarm.js` (niced, in the shared checkout) so the event index and reused queries are warm for the sim code on main. Exit 1 or 2 from prewarm is logged to `~/.cache/hitl-ci/main-guard/<sha>.prewarm.log` and printed, and never marks main red.
Prewarm runs while the guard still holds its lock, so a slow one (15 minute cap, then logged as killed) delays the next main verdict by that long. It runs in the shared checkout, which the guard fast-forwards only when clean and idle; otherwise it warms the older sim code.
The guard only closes or comments on issues it opened itself: each carries a hidden `<!-- main-guard:<label> -->` line in its body, and an open issue under `main-red`, `sweep-finding`, `perf-regression` or `phone-regression` without it is left alone. Other lanes can file under those labels for findings the guard cannot see (a branch, a seeded game) and the guard never touches them; an issue the guard opened before it wrote the marker is not matched either.
